## 2. ビルド

### 2.1 前提

Windows 側に .NET Framework の C# コンパイラが必要です。典型的なパスは `%WINDIR%\Microsoft.NET\Framework\v4.0.30319\csc.exe` です。フォルダ名が `v4.0.30319` でも、インプレース更新により実際のコンパイラや参照アセンブリが新しい 4.x のものである場合があります。厳密な .NET 4.0 API 検査には第 2.3 節を使用してください。

ソースは UTF-8 BOM 付きで格納しています。以下は **cmd.exe 用**のコマンドです。PowerShell の構文ではありません。ソースを置いたディレクトリへ移動して実行します。管理者権限は原則不要です。

### 2.2 Framework コンパイラを直接使用する

```bat
"%WINDIR%\Microsoft.NET\Framework\v4.0.30319\csc.exe" ^
  /nologo /target:winexe /platform:anycpu /langversion:4 /checked- /optimize+ /codepage:65001 ^
  /out:"dnnt_261004_qct5nr_split_zip_extract.exe" ^
  /reference:System.dll /reference:System.Core.dll /reference:System.Windows.Forms.dll ^
  "dnnt_261004_qct5nr_split_zip_extract.cs"
```

`/checked-` は暗号の剰余演算等の前提に合わせた指定です。外部ライブラリの参照はありません。EXE はこのソースだけから生成します。追加の `.csproj`、`.config`、マニフェスト、デザイナーファイルを必須としない構成です。

この方法で選択される標準アセンブリはインストール状態に依存します。これだけで旧 .NET 4.0 の API と完全に照合できたとは扱わないでください。

## 3. 起動と入力

生成した EXE を引数なしで起動すると、すべてのファイルを対象にした複数選択可能な「ファイルを開く」ダイアログを表示します。引数を使う場合は、各ファイルの完全修飾パスを指定します。

```bat
dnnt_261004_qct5nr_split_zip_extract.exe "C:\Archives\sample.zip.aa" "C:\Archives\sample.zip.ab"
```

相対パス、ドライブ相対パス、存在しない入力、異なる親ディレクトリにある入力は受け付けません。入力元がリンクやジャンクションの配下にあること自体は拒否しません。入力名の大文字・小文字、取得できる 8.3 長名、取得できるファイル ID を用いて重複を除去します。ファイル ID による重複除去は同一実体のハードリンクも対象とします。ファイル ID が取得できない場合は、同一 ID と推測して入力を捨てることはしません。

ファイル名に `zip` を含まない入力は除外リストとして表示して処理しません。対象が一つも残らない場合は終了します。対象はファイル名の `StringComparer.Ordinal` 順に処理するため、ASCII 名では ASCII コード順です。自然順ソートではなく、例えば `part10` と `part2` の並びに注意してください。足りない断片を自動検索して追加する処理はありません。

入力ファイルは読み取り専用かつ書き込み・削除共有なしで保持し、処理中の変更を防ぎます。そのため、他のアプリが排他利用している場合等は開始できません。

## 4. モード判定と ZIP 対応範囲

各入力単独での ZIP 構造検証と、全入力を名前順に仮想連結した ZIP の構造検証を行います。EOCD、ZIP64 EOCD / locator、中央ディレクトリ、すべてのローカルヘッダ、ファイル名、サイズ、flags、CRC メタデータ、data descriptor の有無・長さ・値、領域の連続性を照合します。CRC の実データとの比較、Deflate の検証、AES 認証は展開時に行います。

単独 ZIP 群として整合するなら個別複数 ZIP モード、全体の連続ストリームとして整合するなら巨大 ZIP 分割モードになります。一つの入力 ZIP は「個別複数 ZIP モード（単一 ZIP）」と表示します。両候補が成立する曖昧な複数入力、どちらも成立しない入力は選択せず、個別結果と連結結果を表示して終了します。

論理連結ストリームは 64 bit の位置を扱い、必要な入力ファイルの領域だけを読みます。**連結済み ZIP をディスクに作成しません。** 入力ファイル数・エントリ数に比例したメタデータはメモリに保持します。32 bit プロセスでは巨大なエントリ数によってメモリが不足する可能性があります。

対応する主な形式は次のとおりです。

| 項目 | 実装 |
| --- | --- |
| 圧縮方式 | Store (0)、Deflate (8) |
| ZIP サイズ | ZIP32、ZIP64。実装上の長さ上限は符号付き 64 bit |
| data descriptor | 32 bit / 64 bit、シグネチャあり / なし |
| 暗号 | ZipCrypto、WinZip AES AE-1 / AE-2、128 / 192 / 256 bit |
| 整合性 | 展開サイズ、CRC-32。AE-2 は CRC の代わりに必須の HMAC 認証を使用 |
| 名称 | UTF-8 flag、検証済み Info-ZIP Unicode Path、旧式コードページ |
| 日時 | DOS、NTFS extra、Extended Timestamp、旧 UNIX extra |

意図的に受け付けない、または限定対応となる形式があります。

- ZIP 自身のマルチディスク方式、SFX 実行形式、先頭・末尾の付加データ、未参照ローカルレコードや空隙、中央とローカルの矛盾した名前・メタデータは構造エラーです。通常の ZIP として他ソフトが許容しても、本実装は拒否する場合があります。
- Store / Deflate 以外、PKWARE strong encryption、暗号化中央ディレクトリ、patched data 等は対応しません。エントリの範囲を安全に解釈できる場合は個別警告、アーカイブ構造自体を解釈できない場合は判定段階で終了します。
- デジタル署名レコードは構造のみを確認し、署名者の真正性は検証しません。未知の extra field は長さを検査して読み飛ばします。認識した主要 extra field の重複は曖昧な情報として拒否します。

## 5. 日本語名とパスワード

### ファイル名

UTF-8 flag を優先し、対応する Unicode Path extra は元名 CRC と整合性を検査します。符号化情報がない場合、既定では日本語 Windows 用の CP932 として復号し、CP932 で不正なバイト列の場合は CP437 を試します。

文字コードの自動判定は完全にはできません。例えば CP932 としても有効な CP437 名や、UTF-8 flag のない UTF-8 名は、誤った見た目で解釈される場合があります。入力元の仕様に合わせて環境変数 `DNNT_ZIP_CODEPAGE` に `932`、`437`、`65001` 等を指定してください。

```bat
set DNNT_ZIP_CODEPAGE=65001
dnnt_261004_qct5nr_split_zip_extract.exe
```

CP932 の文字内に `0x5c` バイトがあるケースを避けるため、バイト列を文字列に復号してからパス区切りを扱います。ZIP 仕様の正式な区切りは `/` です。本実装では互換性のため `\` も区切りとして受け入れ、両方を Windows の `\` に正規化します。

### パスワード

EXE と同じディレクトリの `password_list.txt` を起動時に読みます。UTF-8、先頭 BOM 任意、1 行 1 候補です。空行と完全一致する重複行は除外します。前後の空白はパスワードの一部として保持します。このファイルは読み取りのみで、追加・更新しません。ファイルの読み取り専用属性は付いていても付いていなくても構いません。ファイルがなければ候補は空、存在して読み取りに失敗する場合はエラーで終了します。

既知候補は出力先への書き込みをせず、サイズ・Deflate・CRC または AES 認証まで実際に検証します。ZipCrypto のヘッダ 1 byte や AES の 2 byte verifier の一致だけでは成功としません。実装差に備え、パスワード文字列の UTF-8、設定コードページ、CP437、現在の ANSI / OEM の重複しないバイト表現も試します。

どの候補も成功しなければ入力を求めます。入力内容は画面へエコーしません。Enter だけの空パスワードも有効な候補です。成功した文字列をメモリ上の先頭へ追加します。大文字・小文字を区別する特殊入力 `ignore` は、その時点のエントリを省略し、以後は既知候補だけを試すモードへ移ります。暗号化されていないファイル、および既知候補で展開できるファイルは引き続き処理します。

`ignore` というパスワードを対話入力することはできません。同じ文字列が本当のパスワードの場合は、開始前に `password_list.txt` に登録してください。空パスワードは空行を無視する仕様のため、初回は対話入力で登録します。

不正なパスワードと暗号データの破損は区別できない場合があります。その場合も仕様どおり再入力または `ignore` の選択を求めます。既知パスワードの検証と実保存のため、暗号化ファイルは成功時でも基本的に圧縮データを 2 回読みます。不一致候補数とデータ量によって追加の時間・I/O がかかります。パスワードや一部の鍵配列は可能な範囲で消去しますが、.NET の不変 `string` や OS のページングを含むメモリ上の完全消去は保証しません。

## 6. 展開先と重複・上書き

「ファイル名を付けて保存」ダイアログで `_dummy.txt` を既定名にします。この架空ファイルは作成しません。入力名を変更しても、その親ディレクトリを展開先として使用します。標準 `SaveFileDialog` にファイル名編集だけを安全・簡単に禁止する設定がないため、ファイル名の変更は許可しています。上書き確認と新規ファイル作成確認は、このダイアログでは無効にしています。

ZIP 内の正規化後のファイルパスを、大文字・小文字を区別せず比較します。重複がある場合、`Y` は以後すべての重複を許可、`y` はその組だけ許可、`n` は中断です。許可した場合も、実際に展開するのは最初の一つだけです。順序はソート済み ZIP の順、その中ではローカルヘッダの出現順です。最初のエントリが後で失敗しても、重複する後続エントリを代わりに使うことはしません。

明示ディレクトリエントリの重複は同じディレクトリとしてまとめ、日時は最初の有効な明示情報を使用します。同じパスがファイルとディレクトリを兼ねる構造、ファイルを親ディレクトリとして必要とする構造は中断します。

事前の物理ファイル上書き確認は `y / n / a / q`、実行中に新たに検出した上書きは `Y / N / y / n / q` です。文字の大小は区別します。事前確認で記録した対象とファイル ID、サイズ、更新日時が変わった場合も、再確認の対象とします。ファイル ID が取得できず同一実体を確認できない環境では、再確認が増える場合があります。明示的な上書き省略と ZIP 内重複の後続省略は失敗に数えません。

展開されたデータは最終ファイルと同じディレクトリの一時ファイルに書き、展開サイズ・CRC・認証を検証してから、開いたハンドルを使って最終名へ改名します。既存ファイルを先に削除しません。一時ファイルは「ZIP を結合したファイル」ではなく、一つの内容ファイルの検証前出力です。検証失敗時は削除しますが、アプリや OS の強制終了、削除権限や共有サーバーの問題では一時ファイルが残る場合があります。

## 7. パスとリンクの安全性

安全性に関するエラーは個別ファイルの警告にはせず、全体を中断します。

絶対パス、ドライブ指定、UNC として始まる ZIP 名、`..` 要素、ADS を作る `:`、NUL 等の制御文字、Windows の禁止文字、予約デバイス名、リンク・特殊ファイル属性を拒否します。`./` と重複区切りを整理し、各要素末尾の空白・ドットを正規化して衝突を検査します。正規化で空になる名前等は拒否します。Unicode 正規化 NFC/NFD により名前を勝手に変更することはしません。

Unicode extra の採用名だけでなく、元バイト列を復号した旧式名とローカルヘッダ側の名にも危険パス検査を行います。中央の external attributes、ASi UNIX / UNIX extra 等から判別できる symlink、デバイス等の特殊オブジェクトも拒否します。

**安全側の追加制限があります。** `FOO~1.TXT` のように 8.3 短縮名に見える名前は、まだ存在しない出力の将来の短縮名まで含めた衝突を事前確定できないため、実際には普通の長い名前として意図されていた場合でも拒否します。既存の展開先ファイルが複数ハードリンクを持つ場合も、確認を通じて上書きするのではなく全体を中断します。これらは一般的な ZIP 展開ソフトより厳しい制約です。

ユーザーが選んだ展開先ルート自身、およびその指定パスの祖先にあるシンボリックリンク・ジャンクションは許容します。一方、展開先ルートから ZIP の相対パスをたどる途中にある reparse point は拒否します。対象ルートのパス要素、および書き出し中の子ディレクトリを、削除・書き込み共有なしのハンドルで保持します。最終要素も no-follow で検査し、検査済み一時ファイルのハンドルを使用して保存します。 属性専用ハンドルに共有制御を依存させないため、固定するディレクトリには `FILE_LIST_DIRECTORY` も要求します。実際の一覧取得はしませんが、書き込み・通過だけ許可され一覧権限がない保存先や祖先では、安全な固定に失敗する場合があります。

この制御は、Windows とファイルシステム / ネットワークサーバーが所定の共有モード、再解析ポイント、ファイル ID、ハンドル操作を正しく実装していることを前提とします。管理者・カーネル権限の攻撃者や悪意のあるサーバーに対する隔離を保証するものではありません。自作コードであることも無脆弱性の保証ではありません。

UNC とドライブ割り当てパスはそのまま使用し、`GetFinalPathNameByHandle` やネットワークドライブの UNC 化 API は使いません。入力の `GetLongPathNameW` は 8.3 名の長名化だけに使用し、リンク先のリアルパス化とは別です。

一部の NAS / ファイルシステムが必要な共有・ハンドル改名・ファイル ID 等を提供しない場合、安全でない代替処理へ切り替えずに失敗します。新規作成したディレクトリの ID が取得できず、後で同一実体を確認できない場合も中断対象です。UNC 対応は任意の NAS に対する動作保証ではありません。

通常の MAX_PATH 制限を使用します。ファイル等の完全パスは 260 文字未満、新規作成ディレクトリは 248 文字未満に制限します。制限を超える内容ファイルは個別警告です。拡張長・デバイス名前空間は使用しません。

## 8. 日時

通常の DOS 日時は ZIP の作成時のタイムゾーン情報を持たないため、実行環境のローカル時刻として解釈します。NTFS の FILETIME と UNIX 系の時刻は UTC として扱います。優先順位は NTFS extra、Extended Timestamp、旧 UNIX extra、DOS 日時の順です。同種の情報ではローカルヘッダ側を優先します。32 bit UNIX timestamp は符号付き値として解釈します。

内容ファイルの作成・更新・アクセス日時は、それぞれ有効な値がある場合に設定し、作成・アクセス日時が省略されている場合は更新日時で補います。新規ファイルでも上書きファイルでも同様です。有効な日時がない場合、OS が設定した値を維持し警告します。日時設定に失敗しても保存内容を破棄せず、警告として記録します。

本処理が新規作成したサブディレクトリだけに日時を設定します。明示された ZIP ディレクトリエントリの日時を優先し、それがなければ重複除去後の展開計画にある子孫ファイルの最も新しい更新日時を作成・更新・アクセス日時に使います。計画段階ですでに保存不能と判定したファイルは、この集計から除外します。後から選択される上書き省略、暗号化 ignore、実行中の失敗によって集計を再計算する設計ではありません。

作成直後に一度設定し、ファイル展開の終了後にも深いディレクトリから再設定します。途中中断時も可能な範囲で後処理を試みます。既存ディレクトリとユーザーが選択したルートの日時は明示設定しません。ただし、そのディレクトリ内のファイルを作成すれば OS 自身が既存ディレクトリの更新日時を変える場合があります。

## 9. エラー、終了、運用上の限界

一つの内容ファイルの CRC 不一致、Deflate 破損、保存不能、未対応圧縮、日時設定失敗などは警告に記録して次へ進みます。危険パス・リンク境界・ZIP の構造不整合、ユーザーの中断は全体を終了します。終了時には成功ファイル数とサイズ、警告、意図的な省略数、末尾が `\` の展開先パスを表示します。途中で全体中断した場合は例外内容を表示し、完了したかのような最終集計は表示しません。

成功または失敗の表示後、コンソールはキー入力待ちになります。対話的なデスクトップ用途を前提とし、無人・サービス実行用のモードはありません。Ctrl+C は可能な場所で中断要求として扱います。ダイアログや入力待ちの状態によっては、直ちに処理を離れないことがあります。

代表的な終了コードは以下です。

| 値 | 意味 |
| --- | --- |
| 0 | 警告なしで完了。承認済みの重複・上書き省略は成功扱い |
| 299 | 完了したが、個別ファイルまたは日時等に警告あり |
| 1223 | ユーザーによる取り消し・中断 |
| 5 | 安全性違反、またはアクセス拒否 |
| 2 / 3 | 入力等のファイル / ディレクトリが見つからない |
| 13 | ZIP の構造不正・形式不正 |
| 87 | 引数不正 |
| 50 | OS または機能が非対応 |
| その他 | 取得できた Win32 エラー、または一般失敗 31 等 |

警告件数は原因メッセージの数ではなく対象ファイル単位を基本とします。内容が保存されていても日時設定に失敗したファイルは警告対象です。ディレクトリの警告は別に表示します。

展開全体を一つのトランザクションとしてロールバックする処理はありません。中断前に確定したファイルや新規ディレクトリは残ります。ファイルを確定する処理も、突然の電源断に対する永続化まで保証するものではありません。

Deflate の距離、ハフマン木、最終ブロック、宣言サイズを超える出力、圧縮データ末尾の余剰等は検査します。ただし、ZIP に宣言されたサイズ自体が巨大であるケースに対する総出力容量・圧縮率・実行時間の独立した上限設定はありません。信頼できない ZIP は、空き容量を確保した専用の展開先で扱ってください。既存の重要データがある保存先では事前にバックアップを作成してください。

#### 6.2 原因の分類と ZIP 仕様との関係

今回は新しい暗号方式や圧縮方式の欠如ではない。サンプルは既存実装が対応する ZipCrypto と Deflate を使用していた。エラーはパスワードを試す前の構造判定で発生している。

PKWARE APPNOTE の bit 3 の書込み規定では、ローカル CRC と両サイズをゼロとし、後続 descriptor に確定値を置く説明がある。本サンプルの非ゼロ暫定 CRC を、仕様が任意値として明示的に許可していると説明することはできない。一方、読み取り実装が descriptor と中央の確定値を照合できる状況で、ローカル暫定値だけを理由に拒否する必要はない。本修正は、実際に流通する作成実装との読み取り互換性を改善するものと位置付けた。

この位置付けの裏付けとして、Info-ZIP 3.0 で無害な合成入力を暗号化し、出力をシークできないパイプへ接続して ZIP を生成した。単なる通常ファイルへのリダイレクトとは分けて検証している。

#### 6.3 「全断片の仮想連結」のエラーが併記された理由

`Detector` は二つの候補を検査するため、個別 ZIP 判定の失敗に加えて、全体を 1 ZIP とみなした候補の失敗も表示する。独立した ZIP 群を単純に連結すると、通常は 1 個の連続 ZIP の中央ディレクトリとして整合しない。したがって、この併記だけで欠落断片や順序違いが確定したわけではない。

指定サンプルは単独 ZIP として構造・内容を検証できた。R02 の対応規則ではこのサンプルを個別 ZIP として受理する。他の入力もすべて単独で有効なら、既存 `Detector` は個別複数 ZIP モードを選択する。今回取得したサンプル以外の 45 ファイルは提供されていないため、元の 46 ファイル全体を実行して確認したとは記録しない。

(1) まず、差分 zip 群を読み込む。従前どおり、コマンドラインで 1 個以上の zip 群が指定されたならば、これらは差分 zip 群である。また、コマンドラインで zip が指定されていないならば、差分 zip 群を開く、[R01.specs] の (1) 入力ファイル群の画定 の (1-2) で規定されているコモンダイアログを用いて zip ファイルを複数個ユーザに選択させる。そして、差分 zip 群について、[R01.specs] の (2) 入力ファイル群の解釈も最後まで実行する。ここまでは、[R01.specs] と変化なしである。ただし、(1-2) の「開く」ダイアログでは、「(1) まず、差分 zip 群を指定してください」というタイトルにする。



(2) 次に、[R01.specs] の (1) 入力ファイル群の画定, (2) 入力ファイル群の解釈 などと全く同一の仕組みを用いて、今度は、ベースライン zip 群を読み込む。これは、コマンドラインにおける zip の指定の有無とは無関係に必ず新たなコモンダイアログで、(1) と同様にユーザに zip ファイル群を選択させる。そして、ベースライン zip 群について、[R01.specs] の (2) 入力ファイル群の解釈も最後まで実行する。ただし、(1-2) の「開く」ダイアログでは、「(2) 次に、ベースライン zip 群を指定してください」というタイトルにする。



(3) ここで、(1) の差分 zip 群と、(2) のベースライン zip 群とは、独立して内部上取り扱う必要がある。混合してはならない。



(4) この段階で、すでに、従前から行なわれている、zip 群の事前検査、モード画定、整合性検査などを実施する。なお、このたび実装する「1. 2 モードハイブリッド方式への対応」も、差分 zip 群、ベースライン zip 群に対してともに実装されている必要がある。



(5) (4) により、差分 zip 群、ベースライン zip 群のそれぞれに含まれるコンテンツファイルのディレクトリツリー構造が判明するので、ベースライン zip 群を展開し、次に、差分 zip 群を上書き展開する。

&#x20;   ここで、差分 zip 群と、ベースライン zip 群の意味が重要となる。

&#x20;   \- ベースライン zip 群とは、ある何らかのユーザディレクトリコンテンツの特定のバージョンを、まとめて zip 群にしたものである。

&#x20;   \- 差分 zip 群とは、ベースライン zip 群よりも事後に、同じ何らかのユーザディレクトリコンテンツの特定のバージョンを、まとめて zip 群にしたものである。ただし、容量を節約するために、「ベースライン zip 群」よりも後に追加・変更されたファイルのみが、「差分 zip 群」に含まれている。

&#x20;   \- 問題は、ベースライン zip 群を作った人と、差分 zip 群を作った人とで、少し趣味が異なるなどして、根っ子のほうのディレクトリ名が随分違うことがある。そこで、本プログラムは、「ベースライン zip 群」と「差分 zip 群」との相互の内部仮想ディレクトリツリーを探索し、「差分 zip 群」におけるあるできるだけ根元のディレクトリが、「ベースライン zip 群」のあるできるだけ根元のディレクトリと相対的に対応するというその最も最適な対応関係を導出する (2 つのフォルダ構造体の摺り合せにより、双方の基準ディレクトリを選定する、マッチング・アルゴリズム)。

&#x20;       \- このアルゴリズムは、次のとおりである。「ベースライン zip 群」と「差分 zip 群」のそれぞれのディレクトリ構造を根っ子からみていく。「ベースライン zip 群」 側の M 階層目に該当するあるディレクトリ d を基準とした下位ディレクトリ構造 P (d に含まれる再帰的にみたファイル群およびフォルダ群) と、「差分 zip 群」 側の N 階層目に該当するあるディレクトリ e を基準とした下位ディレクトリ構造 Q (e に含まれる再帰的にみたファイル群およびフォルダ群) とがあるとする。P と Q の一致度合い、すなわち同一の再帰的にみたファイル群またはフォルダ群の一致の個数 c が最大となる d, e を発見したとき、それは、「「差分 zip 群」におけるあるできるだけ根元のディレクトリが、「ベースライン zip 群」のあるできるだけ根元のディレクトリと相対的に対応するというその最も最適な対応関係」として、望ましい。ここで、d と e のディレクトリ名は異なる可能性があることに留意する。

&#x20;       \- たとえば、ベースライン zip 群の内容物が [T261007_EL_VCLTC_14]、差分 zip 群の内容物が [T261007_EL_VCTTJ_15] とする。ここで、ベースライン ZIP 群の「dir_abc/dir1/」ディレクトリには file1.md (A) と folder1/test.txt (B) がある。同様に差分 zip 群の「dir_sheep/dir_neko/dir2/」ディレクトリにも file1.md (A) と folder1/test.txt (B) がある。すると、d は「dir_abc/dir1/」、e は 「dir_sheep/dir_neko/dir2/」としたとき、c は、2 であり、他のあらゆる可能性よりも最大である。よって、ベースライン ZIP 群における「dir_abc/dir1/」と、差分 ZIP 群における「dir_sheep/dir_neko/dir2/」は、差分関係において同一の基準ディレクトリであるといえる。

&#x20;       \- この処理は、「ベースライン zip 群」と「差分 zip 群」のそれぞれのディレクトリ構造に、合計数十万個のファイルやディレクトリ構造が存在しえるので、そのような場合においても極めて高速に最良の基準ディレクトリ (c が最大となる) を発見しなければならない、という点で、特に注意を要する。すなわち単純なループを書くと、構造物の個数に対して指数的に遅くなる可能性があるので、それを避けるために、適切なデータ構造を前処理として構築し、その構造相互間を高速に一致検査する必要がある。ここにおいて AI はこの処理の本質的特性を理解し、最良のアルゴリズムを構築せよ。当該アルゴリズムについては、日本語として分かりやすくかつ詳細に history およびプロンプト応答本文において解説をせよ。必要に応じてアスキーアートを用いて (図ファイルは不可) 原理もわかりやすく解説せよ。

### 6. 今回の実装内容

#### 6.1 ハイブリッド認識

認識の候補は次の三つであり、いずれも `ZipReader.Read` による構造検証を必要とする。

1. 入力物理ファイルが、すべて独立した ZIP である。
2. 従来のファイル名 Ordinal 順に全物理ファイルを仮想連結すると、一つの ZIP になる。
3. 同じ `Q.zip` の `P` が 2 個以上ある群を推定し、群ごとに `P` の Ordinal 順で連結する。群外のファイルは単独 ZIP として扱う。

`Q` および `.zip` の比較には Windows の通常の同名判定に合わせた `OrdinalIgnoreCase`、`P` の並びには大文字小文字を区別する `Ordinal` を使う。P は ASCII 英数字のみで、同じ群では同じ長さでなければならない。異なる群の P の長さや形式は独立してよい。

単独検査の結果や、同じ断片順の全体連結結果は再利用する。全体連結と一群だけの群別連結が同じ物理断片を同じ順で参照する場合、それらを同じ解釈として扱う。異なる断片順や異なる論理 ZIP 分割で複数の完全な解釈が成立した場合は、詳細を示して拒否する。

欠落判定のために `a` から始まる、`0001` から始まる、数字が必ず 1 ずつ増える等の未指定規則は導入していない。内容の欠落・順序違いは、仮想連結後の ZIP 構造で検出する。旧例の `.01.zip.a / .02.zip.b / .03.zip.c` のように各 Q へ 1 個ずつ存在する入力も、従来の全体連結によって認識できる。

#### 6.2 基準ディレクトリの照合アルゴリズム

候補ごとに、その基準自身を除く子孫の「相対パス＋種別」の集合を考える。集合の共通要素をファイルとディレクトリに分けて数え、その合計を最大にする。サイズは照合点数に含めず、元の非圧縮 bytes の統計として保持する。

暗黙ディレクトリも補う。仮想ルート / は深さ 0 の候補であり、自身をディレクトリ総数に加えない。最大一致の次に深さ合計を最小化し、なお同点の別候補が残れば具体的な二組を示して拒否する。

##### 6.2.1. 最初の効率化：一致し得ない名前を照合から除く

両方のツリーを先に読み、すべての直下要素の「名前＋種別」を共通の整数へ変換する。その名前・種別がベースライン側だけ、または差分側だけにしか出現しないなら、その要素はどの基準対に対しても相対パスの最初の一致要素になれない。

たとえば、両側のどこにも対応名がない `B_ONLY_123.dat` は照合点数に寄与しない。これを照合用の部分木から外しても c は変わらない。ディレクトリの場合も、その名前が他方に一度もなければ、親を基準とした相対パスではその先のすべてが一致しないので、親の照合用構造からその枝を外せる。

ただし、そのディレクトリ自身は別の基準候補として処理する。双方の基準ディレクトリ名が異なることを許す仕様を、この操作で損なわない。削るのは照合用の表現であり、展開対象や元の統計は残る。

この処理を「投影」と呼ぶ。大きな効果がある例は、50,000 個のコピーがそれぞれ共通の `README` と固有名ファイルを持つ入力である。固有名が他方には存在しなければ、50,000 個のコピーを照合するための構造はすべて同じ `README` 一個へ揃う。

##### 6.2.2. 二つ目の効率化：同じ部分木を一つの構造 ID へまとめる

各ディレクトリを子から親へ処理し、投影後の直下要素を「名前＋種別」の整数順に並べる。ファイルには名前と種別を、ディレクトリには名前、種別、その下位部分木の構造 ID を記録する。この整列済み配列が完全に同じなら、同じ構造 ID を割り当てる。

下位 ID の等価性を子から順に確定しているので、同じ ID は、その基準からの全相対パスと種別の集合が完全に等しいことを意味する。親の名前を構造 ID に含めないため、`release_a/core/` と `archive_b/payload/` のように基準名が違っても、配下構造が同じならまとめられる。

辞書のハッシュは比較先の振り分けに使い、最終的には配列の長さとすべての名前・種別・下位 ID を厳密に比較する。ハッシュ値の衝突を構造一致と誤認しない。

同じ構造 ID を持つディレクトリ群は、相手が同じなら c もすべて等しい。そこで各 ZIP 群について、各構造 ID の最浅ディレクトリだけを代表にする。同じ最浅深さに複数の実ディレクトリがあれば、そのうち二つを保持する。最大一致の構造対が見つかったとき、二つ目の代表の存在から自動選定の曖昧さを検出できる。

これにより、同じ構造がベースラインに 50,000 個、差分にも 50,000 個ある場合も、その 25 億組を個別に保存・比較する必要はない。構造対を一度評価し、各側の最浅代表の数で一意性を判定できる。

##### 6.2.3. 構造どうしの一致個数を厳密に計算する

異なる構造同士の交差は、直下要素の名前・種別が一致するところだけを処理する。

| 一致した直下要素 | 加えるもの |
| --- | --- |
| ファイル | ファイル一致を 1 |
| ディレクトリ | ディレクトリ一致を 1 と、その下位構造どうしの一致個数 |
| 名前または種別が異なる要素 | 0 |

この式は、相対パスを最初の一要素で分けたものである。一つの相対パスは必ず一つの直下要素の下に属するため、二重計数も取りこぼしも生じない。

直下配列は整列済みなので、二本の位置を進めながら一致する要素だけを見つける。構造 ID が同じなら、投影後の全ファイル数・全ディレクトリ数がそのまま交差件数になり、下位を読む必要がない。

処理はメソッドの再帰呼び出しではなく、明示的なフレーム一覧で進める。したがって、極端に深い入力でも、この照合処理が呼出しスタックの深さ制限に達することを避けられる。

計算済みの構造対には固定 262,144 枠、約 6 MiB のキャッシュを用いる。交差は対称なので、左右を入れ替えた同じ構造対は同じキーにする。キャッシュの枠が上書きされた場合、必要になれば同じ厳密計算をやり直す。この容量は正しさや探索範囲を制限せず、再計算回数にだけ影響する。

##### 6.2.4. 三つ目の効率化：正の一致があり得る候補だけを列挙する

c が正であるためには、少なくとも一つ、名前と種別が一致する直下要素が必要である。深い場所のファイルが一致する場合でも、そこへ至る相対パスの最初のディレクトリは必ず一致している。

この性質を使い、差分側について「この名前・種別の直下要素を持つ構造 ID の一覧」という転置索引を作る。ベースラインの構造を一つ取り出したら、その直下要素の索引だけを引けばよい。共通の直下要素がない構造対は候補にならない。

一つの構造対が複数の直下要素から引かれた場合は、差分の構造 ID を添字とする世代番号配列で重複を除く。全候補対の集合をメモリに溜め込む必要はない。この配列の大きさは、両側を合わせた構造数に比例する。

最初に両側で同一 ID を持つ構造対を評価する。これらは交差件数が即座に分かるため、以後の枝刈りに使う強い暫定最大値を早く得やすい。

##### 6.2.5. 四つ目の効率化：勝てない候補と索引一覧を上界で省略する

候補対の投影後ファイル数を `Fb, Fd`、ディレクトリ数を `Db, Dd` とすると、交差件数には必ず次の上界がある。

`c <= min(Fb, Fd) + min(Db, Dd)`

この上界が現在の最大一致数未満なら、その候補対は調べない。上界が同点でも、最浅代表の深さ合計が現在の最良より大きければ調べない。同じ最大一致数・同じ最小深さで二組をすでに確認しているなら、その順位と同じ候補をさらに数える必要もない。より良い順位を作れる候補の調査は続ける。

さらに転置索引の一覧ごとに、含まれる候補の最大ファイル数、最大ディレクトリ数、最小深さを保持する。これらから計算した保守的な上界・深さ下界で一覧全体が勝てないと分かれば、その長い一覧自体を走査しない。

この一覧単位の枝刈りは、各コピーが `README` と「両側で共有されるコピー固有ファイル」の二個を持つケースで効く。固有ファイルも両側に存在するため、単純な投影だけでは 50,000 種類の構造が残る。それでも同じ構造同士の初期評価によって c = 2 の同点候補が二組見つかれば、二個しか要素を持たず、同じ深さの他のコピー対を走査しても順位は改善しない。共通 `README` の巨大な索引一覧を一括して省略できる。

##### 6.2.6. 正しさを保つ理由

投影で外した枝は、他方に存在しない名前・種別で始まるため、どの候補対でも一致に寄与しない。部分木 ID は厳密な子配列比較で作るため、同じ ID の交差は正確に同じである。同じ ID の候補を最浅代表へまとめても、c の最大化と深さ合計の最小化は変わらない。

正の一致を持つ構造対には共通の直下要素が必ずあるので、転置索引はそのような対を漏らさない。探索途中に省略するのは、数学的な上界と深さ下界から、順位の改善にも未検出の同点の発見にも寄与しないと証明できる対だけである。残った交差は直下要素ごとの分解式で厳密に数える。

したがって、候補の抽出、構造の圧縮、枝刈り、固定容量キャッシュは、近似値やサンプリングへ置き換える処理ではない。得られる候補と拒否結果は、元の相対パス集合をすべてのディレクトリ対で比較した結果に一致する。

##### 6.2.7. 計算量と限界

前処理は、パスの読み取り・必要な親パスの構成、直下要素の整列、構造の同一化、転置索引の構築から成る。ファイル・ディレクトリを N 個、異なる投影後構造を S 個とすると、構造表、転置索引、候補の世代番号配列は元のツリーに比例する規模に収まり、全候補対の個数に比例する表を持たない。極端に深い入力では、完全な相対パス文字列を各ディレクトリに保持する分の文字数もメモリに影響する。

実際の探索時間を決めるのは、異なる構造の数、共通の直下要素の頻度、上界で省略できなかった索引走査の数、再利用できなかった下位交差の量である。コピー構造の多い入力や、対応部分が大きく共通している入力では、構造共有と強い最大値により比較数を大きく減らせる。

任意の入力に対する線形時間や一定秒数は保証しない。たとえば、多数の互いに異なる平坦なフォルダがそれぞれ多数の共通ファイル名を持つ問題は、任意の集合対から共通要素数が最大の組を探す問題を含む。上界が十分に絞れない構造では、異なる構造数の積に相当する候補を調べる場合がある。固定容量キャッシュの追い出しによって再計算が増える場合もある。

本実装は、こうした一般の最悪入力まで軽いと説明するのではなく、厳密性を保持したうえで、反復構造、同一部分木、寄与しない名前、候補上界を活用する。候補が多いという理由で途中の候補を切り捨てたり、最適性を確かめずに最初の対応を採用したりはしない。処理中も既存のキャンセル判定を呼び出す。

#### 6.3 差分配置と省略・復元

差分側はコマンドラインまたは差分用の開くダイアログで選択する。その ZIP 認識と仮想パス検査を終えてから、ベースラインを新しいダイアログで選択する。両者の `SourceSet`、認識結果、エントリ、重複判定は独立している。

各入力群内の同名ファイルには既存の確認と先勝ち規則を適用する。その後に基準を計算し、ベースラインだけの `Relative` を出力パスへ変換する。`Name`、`Archive`、CRC、オフセット、暗号情報、サイズ、日時は変えない。物理保存先が選ばれてから、新しいすべての出力パスを既存の `SafeRoot` と上書き検査へ渡す。入力元自身への上書き検査は、両入力群の実体識別子を対象とする。

提示例の対応:

| 元の内容 | 出力先に対する相対パス・取扱い |
| --- | --- |
| ベースライン `dir_abc/dir1/file1.md` | `dir_sheep/dir_neko/dir2/file1.md`。差分に同じ保存先があるため、通常はベースライン展開を省略する。 |
| ベースライン `dir_abc/dir1/folder1/test2/test.txt` | `dir_sheep/dir_neko/dir2/folder1/test2/test.txt`。差分にないのでベースラインを保存する。 |
| 差分 `dir_sheep/dir_neko/dir2/folder2/test3/test4.txt` | 元の差分相対パスのまま追加する。 |
| 差分 `computer.md` | 出力先の直下へ保存する。基準の外でも除外しない。 |
| ベースライン `dir_abc/dir2/super.txt` | `_base_misc_files/<日時>/dir_abc/dir2/super.txt`。元の階層を保持する。 |
| ベースライン `dir_defg/readme.txt` | `_base_misc_files/<日時>/dir_defg/readme.txt`。入力にない `aaa.txt` へ改名しない。 |
| 差分 `dir_dog/dir_orange/readme.txt` | そのまま保存する。入力にない `piano.txt` へ改名しない。 |

提示例は、ベースライン 7 ファイル＋差分 7 ファイルから 2 ファイルを置換するため、**最終的な有効保存計画は 12 ファイル**になる。そのうち 3 ファイルはベースラインの基準外から退避する。

差分による置換対象は、正常時にはベースラインの圧縮データもパスワードも読み出さない。メタデータだけの省略なので効率がよい。一方、差分ファイルが破損・未知パスワードの ignore・保存失敗になった場合は、対応するベースラインを使って復元を試す。この復元にも差分ファイルと同じ `OverwritePolicy` を使用するため、上書きの許可範囲を拡大しない。ユーザーが `n/N` で上書きを拒否した場合は復元もしない。安全性違反、中断、事前検査エラーを迂回しない。

復元が成功しても新しい差分内容を適用できたわけではない。警告には差分失敗とベースライン復元を明記し、通常成功とは区別する。

#### 6.4 衝突・日時・画面操作

合成後にファイルとディレクトリ、親ディレクトリとの衝突を再検査する。予約した `_base_misc_files/<日時>/` と、差分の元内容または再配置したベースライン基準配下が重なる場合は、例外で止める。既存の物理ファイルとの上書きは従来の確認方式を使う。

同一入力群内の明示ディレクトリ日時は最初の有効なものを採用する。両入力群に同じ出力ディレクトリの明示日時がある場合は、差分側を優先する。明示日時がないディレクトリについては、既存の計画集計と、作成時・展開後の深い順の再設定を維持する。

入力ダイアログで OK になった直後、最初に選択されたファイルの親を `HKCU\Software\DNNT\dnnt_261004_qct5nr_split_zip_extract` の値へ保存する。

| 用途 | レジストリ値 |
| --- | --- |
| 通常モードの入力／差分モードの差分入力 | `SourceDialogDirectory`（既存値を共有） |
| 差分モードのベースライン入力 | `BaselineSourceDialogDirectory`（R03 で追加） |
| 保存先ダイアログの初期位置 | `DestinationDialogParentDirectory`（既存挙動を継承） |

ダイアログ履歴が利用できなければ既存の初期位置へ戻る。コマンドライン入力の検証後にも入力元の履歴を更新する従来の挙動は維持した。保存先のダミー名を入力ファイル名から作る既存改修も維持した。

起動時はモードを最初に表示する。入力・保存ダイアログには指示されたタイトルを設定する。基準の統計、共通ファイル・ディレクトリ数、ベースラインの省略予定数・非圧縮 bytes は計算直後と差分展開終了時に同じ内容を表示する。

正常終了時の `e/E/o/O` は、Windows ディレクトリ内の `explorer.exe` を明示し、出力先を一つの引用符付き引数として渡す。シェルのコマンド文字列を組み立てない。ルート末尾の逆斜線も引数の引用に対応する。

#### 8.2 制約・未検証範囲

ネイティブ .NET／Mono の起動は実行環境の制約により利用できなかったため、管理コード部分の検証には上記 WASM 環境を使った。これは検証用の手段であり、納品プログラムへ Mono・WASM・Node の依存を追加したものではない。

**Visual Studio 2026 の標準の対応一覧には .NET Framework 4.0 が掲載されていない。** そのため「VS 2026 を標準インストールすれば、そのまま必ずビルド可能」とは確認できない。要求された Framework 4.0 を維持し、その正式な参照アセンブリに対するコンパイルを確認した。既存プロジェクトを利用する場合は、その環境で利用できる適切なコンパイラ・参照設定が必要である。次項に、メインソース単独で依存 API を固定した Windows 用コマンド例を示す。

- この照合はパス構造を基準にした最大一致であり、同じ名称が偶然一致した異なる製品・フォルダを意味的に識別するものではない。ゼロ一致、最良候補の同点、ベースラインの両件数が半数未満、配置衝突は自動停止する。
- 完全に異なる部分木が大量にあり、共通名も密に重なる場合、候補計算量は大きくなり得る。任意入力で線形時間になるとは主張しない。全候補対を保存せず、固定容量キャッシュと定期的なキャンセル確認を使用する。

#### 8.3 適用・使用方法

既存プロジェクトの `dnnt_261004_qct5nr_split_zip_extract.cs` の内容を、今回の R03 ソースの内容で置き換える方法なら、現在の `Compile Include` を変更しなくてよい。R03 のバージョン付きファイル名で登録する場合は、旧本体をコンパイル対象から外し、新本体 1 個だけを登録する。`Lib.cs` 等の既存ファイルを同時に差し替える必要はない。

通常モードは従来どおり起動する。入力をコマンドラインで渡す場合は完全修飾パスを指定する。

~~~bat
dn_multiple_zip_extractor.exe "C:\backup\source.01.zip" "C:\backup\source.02.zip"
~~~

差分モードの例:

~~~bat
dn_multiple_zip_extractor.exe /d "C:\backup\diff.01.zip" "C:\backup\diff.02.zip.a" "C:\backup\diff.02.zip.b"
~~~

この例の引数は差分 ZIP 群である。続いて表示されるダイアログからベースラインを選び、基準の表示を確認して出力先を指定する。`/d` だけで起動すれば、最初に差分 ZIP 群の選択ダイアログも表示される。`-d` でも同じ動作になる。

本体単独の明示的な .NET Framework 4.0 API ビルド例は次のとおり。**Windows の cmd.exe 用**であり、`DNNT_REF4` とコンパイラはその環境に存在する正規のものを指定する。

~~~bat
set "DNNT_REF4=C:\Program Files (x86)\Reference Assemblies\Microsoft\Framework\.NETFramework\v4.0"
"%WINDIR%\Microsoft.NET\Framework\v4.0.30319\csc.exe" ^
  /nologo /noconfig /nostdlib+ /target:winexe /platform:anycpu /langversion:4 /checked- /optimize+ /codepage:65001 ^
  /out:"dnnt_261004_qct5nr_split_zip_extract.exe" ^
  /reference:"%DNNT_REF4%\mscorlib.dll" ^
  /reference:"%DNNT_REF4%\System.dll" ^
  /reference:"%DNNT_REF4%\System.Core.dll" ^
  /reference:"%DNNT_REF4%\System.Windows.Forms.dll" ^
  "dnnt_261004_qct5nr_split_zip_extract_r03_261007_vgd8la.cs"
~~~

このソースは既存の `Exe` プロジェクト設定でも、上記の `WinExe` 設定でも使えるように `Native.EnsureConsole` を継承している。ここで提示した Windows コマンドや、Visual Studio 2026 の IDE 操作を今回実行したわけではない。
