### 5.4. 物理パス、リンクの実体、ZIP 内の相対名

`InputRoot.Read` は入力パスの種類と読取可否を確認する。`FileSnapshot` と `DirectorySnapshot` は、ハンドルから実体パス、ボリューム番号とファイル ID、サイズや更新時刻を採取する。`FileSnapshot.Open` は読み直す際にこれらを照合し、列挙後の変更・置換を検出する（原本 475–495、632–643、657–687 行）。

`Manifest.Build` は入力を共通の名前空間へ登録する。通常ファイルはファイル名をルート直下に置く。物理ディレクトリは、指定されたディレクトリ名を ZIP 内のルート名にして配下を保存する。明示指定 ZIP は最後の `.zip` 拡張子を除いた名前を仮想ルートとして使用する。入力ディレクトリの内部にある ZIP は通常ファイルとして圧縮し、再帰的には展開しない（原本 1367–1444 行）。

`Manifest.AddDirectoryTree` は明示スタックでディレクトリを走査する。ZIP 内の相対名は指定されたリンク側の名前を保ち、リンク先の物理名へ置換しない。`Native.OpenReadDirectory` と `Native.OpenReadFile` は入力で `OPEN_REPARSE_POINT` を使用せず、リンク先の実体を開く。生成側の `WriteCentral` は通常ファイル／ディレクトリの DOS 属性を記録し、入力リンクの属性を ZIP に引き継がない（原本 1451–1488、2108–2112、2144–2154、2441–2458 行）。

循環検出には全体の訪問済み集合を使わず、`DirectoryWork.FindAncestor` が現在の親鎖と実体 ID／実体パスを比較する。同一実体へ到達する別枝は、それぞれ別の相対名として保存する。祖先へ戻る循環だけは通常フォルダとして登録し、警告して再下降を止める（原本 1463–1472、1602–1608 行）。

名前の重複は `Manifest` の大文字小文字を無視する辞書で検出する。ファイル同士、ファイルとディレクトリ、親がファイルである場合の衝突を拒否する。ディレクトリ同士は統合できる。末端の空ディレクトリは明示エントリとして保存し、ZIP 内パスが UTF-8 で 65,535 bytes を超える場合は拒否する（原本 558–568、1424–1439、1521–1585 行）。

### 5.5. 事前圧縮、キャッシュ、配置計画

`Precompress` は最大 8 ワーカーで各入力を独立に読んで圧縮し、平文長、CRC、SHA-256、圧縮長を確定する。本出力と同じ `CreateCompressor` を使用する。ZIP 入力も復号・展開してから新たに圧縮し、元 ZIP の圧縮済みストリームをそのまま再利用しない（原本 279–346 行）。

`CompressedCache` は圧縮済みデータを 64 KiB の断片で保持する。作成途中も含めて管理オブジェクト分を計上し、共有ロックで競合を防ぎ、FIFO で古いものから破棄する。予算は使用可能な物理メモリ、コミット可能量、プロセスの空き仮想空間の最小値の 80% として再評価する。キャッシュ不足や配列確保失敗でも、計測・再圧縮による処理を続ける設計である（原本 778–940、1963–1975 行）。

`PackingPlan` は、ZIP のローカルヘッダ、中央ディレクトリ、ZipCrypto ヘッダ、data descriptor、ZIP64 境界まで含めた完成サイズを使う。入力順 first-fit、大きい順 first-fit／best-fit を比較する。通常容量で個数上限に収まらない場合は LPT 型の均等配置、容量探索、有限回数の移動・交換改善を行う。数学的な大域最適や最少個数を保証するアルゴリズムではない。計画確定時には各入力がちょうど 1 回だけ配置され、個数が設定上限および 9999 個以下であることを確認する（原本 1052–1343 行）。

### 5.6. 出力名と削除・作成の安全性

`OutputNames.PartPath` は、生成数が 1 なら指定名、複数なら確定した生成数に応じた 2／3／4 桁の連番を 1 個目から一律に付ける。設定上限ではなく実際の生成数を使う。10000 個以上は計画検査の時点で例外となる（原本 1306–1309、1635–1663 行）。

`DirectoryGuard` は出力フォルダをリンク解決済みの実体に固定する。`RemovePreviousOutputs` は出力直下だけを列挙し、指定名または厳密な ASCII 2～4 桁連番名に一致する候補を検査する。候補のディレクトリ／リンク、読み取り専用、入力自身や入力のハードリンクを拒否する。削除前に一覧を示して確認し、名前を再検索せず、取得済みハンドルに削除保留を設定する（原本 1677–1694、1704–1723、1764–1810 行）。

`ZipSource` は中央ディレクトリ、ローカルヘッダ、ZIP64 extra、data descriptor、各データ領域の位置と長さを検査する。名前は UTF-8 フラグ、CRC が一致する Unicode Path extra、既定の CP932 の順で解釈し、CP932 として不正な旧名だけ CP437 で再解釈する。明示 UTF-8 の不正を別の文字コードで救済しない（原本 2994–3310 行）。

AppContext.SetSwitch("Switch.System.IO.UseLegacyPathHandling", false);

通常表記の `Path.GetFullPath()` を維持し、まず標準の正規化と既存の名前検査を済ませる。Microsoft のパス形式資料では、`GetFullPathName` は接頭辞なしでも MAX_PATH 超の文字列を処理できると説明されている。独自のドット・UNC 正規化器への置換は行っていない。[参考: Microsoft のパス形式](https://learn.microsoft.com/en-us/dotnet/standard/io/file-path-formats#skip-normalization)、[互換スイッチと長いパス](https://learn.microsoft.com/en-us/dotnet/framework/migration-guide/retargeting/4.6.x)

### 6.2. 3 種類のパス表記を混同しない

| 用途 | ドライブの例 | UNC の例 |
|---|---|---|
| 入力・表示・実体比較 | `C:\data\deep\file.txt` | `\\server\share\deep\file.txt` |
| 内部の属性・列挙・Win32 I/O | `\\?\C:\data\deep\file.txt` | `\\?\UNC\server\share\deep\file.txt` |
| ZIP 内の相対名 | `data/deep/file.txt` | 指定されたルート名に従う相対名 |

`ToExtendedPath()` はドライブと UNC の変換を分け、拡張長表記が 32,767 UTF-16 単位以上になる場合を拒否して終端 NUL の余地を残す。最終的な許容長は Windows／ファイルシステムの制約も受ける。`FromExtendedPath()` は API 結果を通常表記へ戻す。元の `Native.FinalPath()` と同じ復元規則を共有することで、入力・出力の実体比較へ接頭辞が混ざらないようにした。

`Native.GetAttributes()` は `File.GetAttributes()` に拡張長表記を渡す。`Native.GetFileSystemEntries()` は同じ表記で直下だけを列挙し、返す配列を通常表記へ戻す。並べ替え・スタック走査・例外伝播は従来のままである。

`Native.OpenHandle()` は `CreateFileW()` に渡す直前だけ変換する。`CONIN$` は終了キー待機用デバイスなので変換しない。アクセス権、共有モード、作成条件、フラグ、SafeFileHandle の所有権は変更しない。

この明示的な拡張長 I/O を使用する方式は、接頭辞なし Win32 長パスの有効化に必要なレジストリ・マニフェスト設定をユーザーへ要求しない。[参考: Maximum Path Length Limitation](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)

### 6.3. [T261008_EL_VETQL_05] と既存の保護を維持

## 8. 制約・懸念・結果の限界

### 8.1. 今回の対応範囲と残る長さ制限

長いパスへの対応対象は圧縮元である。出力は従来どおりフルパス 260 文字未満、ファイル名 255 文字以下であり、保存先リンクを解決した実体側にもこの制限が適用される。Windows／ファイルシステム固有の上限と、ZIP 内ファイル名の UTF-8 65,535 bytes 上限も残る。入力には通常のドライブ絶対パス／UNC を指定し、拡張長接頭辞を直接付けない。

### 8.2. 新しい .NET パス正規化に伴う狭い互換差

旧 .NET のパス処理が正規化して受理していた、途中成分の末尾空白などを含む表記は、新しい処理で既存の安全な成分検査により拒否される場合がある。例えば `C:\data \file.txt` のような表記である。Microsoft は、4.6.2 以後の正規化が途中ディレクトリ成分の末尾空白等を従来のように除去しないことを説明しており、これはその変更と既存 `ValidateComponent` の組合せから導かれる互換差である。通常の実在名を使う長い入力への対応を目的とし、予約デバイス名・ADS・危険な ZIP 相対名の検査は緩めていない。[参考: Mitigation: Path Normalization](https://learn.microsoft.com/en-us/dotnet/framework/migration-guide/mitigation-path-normalization)

### 8.3. 既存の動作上の制約

- 祖先へ戻る循環は通常フォルダとして残し、警告してその枝の下降だけを止める。同一実体への別枝は保存する。
- 元 ZIP は既存の Store／Deflate、ZipCrypto／WinZip AES 等の対応範囲内に限る。ZIP 内リンクや特殊ファイルを展開する追加機能はない。
- キャッシュ利用時は実体・サイズ・日時等を照合するが、外部から入力が更新され続ける運用を完全なスナップショットにする仕組みではない。
- 詰め込みは有限のヒューリスティックであり、不可分の大ファイルや入力の分布により、完全な均等サイズ・最少個数・大域最適は保証しない。
- 旧出力は確認後に削除するため、その後の失敗で旧 ZIP を復元する機能はない。新規出力の後片付けも、OS の拒否などで失敗した場合は詳細を表示する既存設計である。

### 8.4. 実証できていない事項

この環境は Linux で、C# コンパイラ、MSBuild、.NET Framework 参照アセンブリ、Windows／Wine がない。したがって **Visual Studio 2026 でのビルド合格、C# 自己テスト合格、Windows の実ファイルを用いた長パス圧縮の成功は主張しない**。ソース・設定・境界計算・差分の確認結果と、実際のコンパイル・Win32 実行結果を分けて扱う必要がある。
